Three of today's stories ask the same question from different sides: what can an AI tool reach once it is running on someone's machine? Start with the expensive answer.

## 🔥 Binance says an internal AI tool was the pivot in its $6.34 billion breach
Binance published its findings on 3 November. Binance describes a campaign that began with a tampered Homebrew installer in June and a fake job-interview process in September. On 20 October they used a compromised engineer's computer and an internal AI tool to take control of a wallet DevOps engineer. Binance says that engineer had a container deployment permission token on his computer, and the attackers used it on 29 October to deploy a container and run a malicious script.

Binance puts about USD 6.34 billion of assets as impacted, about USD 2.85 billion frozen or intercepted, and says 98% of the affected token assets had been replenished by 31 October. It doesn't name the AI tool, and it publishes no hashes, domains or wallet addresses. The design lesson doesn't need those: an assistant that can act on engineers' behalf inherits their reach, and a deploy token sitting on a laptop becomes the prize. Treat an internal AI tool like a privileged service account, not a convenience.

**Affected:** an unnamed internal AI tool and a DevOps engineer's machine holding a container deployment token · **Fixed in:** not applicable, Binance says it rebuilt the tool and its access controls · **Severity:** not stated, Binance puts about USD 6.34 billion as impacted · **Stopgap:** Binance says it suspended withdrawals and revoked on-chain EIP-7702 authorizations · **If compromised:** Binance says it decommissioned credentials and tokens tied to the affected engineers and replaced affected devices
[Source](https://www.binance.com/en/blog/community/3229153443759566763)

## 🚀 Cogent's VR-1.1 repairs 57.9% of CVEs on a public benchmark, by Cogent's own count
Cogent Security released VR-1.1 on 3 November, a model aimed at fixing vulnerabilities rather than finding them. On LiveCVEBench, a benchmark of 190 tasks across 14 languages from researchers at Harbin Institute of Technology and Kuaishou, Cogent reports 57.9% of tasks repaired against 45.3% for both Claude Code and Codex.

Cogent ran the comparison itself, and it says inference budgets differed across the three systems. Neither the press release nor SiliconANGLE says how customers can get VR-1.1, so there's nothing to test today. If you do patch triage with agents, the interesting part is the setup: network blocked during repairs and grading tests hidden until the agent finished. That's a good template for your own evals.
[Source](https://siliconangle.com/2026/11/03/exclusive-cogent-securitys-vr-1-1-model-outscores-claude-code-and-codex-on-vulnerability-repair/) · [Press release](https://www.prnewswire.com/news-releases/cogent-unveils-vr-1-1--its-latest-frontier-cyber-model-which-tops-livecvebench-for-vulnerability-repair-302927966.html)

## 🤖 Postman's desktop app has been installing agent plugins on its own
A GitHub issue opened on 25 October, which hit the Hacker News front page, reports that opening Postman desktop made Codex and Claude Code install a Postman plugin, a session-start hook, a remote MCP connection and a CLI. The hook tells agents to load a Postman skill before any non-trivial API engineering task, and the installer approves Postman's own hook after installing it. The reporter calls it a consent and trust-boundary problem.

Postman replied on 3 November that it bundles these because users struggled to wire them up, that they can be removed from inside the app, and that it will make the opt-in clearer. The issue is still open. Whatever you think of the product, the pattern matters: an app on your laptop can edit your agent's startup instructions. Know which of your tools may write to agent config.

**Try this:** on one laptop, list the plugins, hooks and MCP servers Codex and Claude Code have registered, and note which app added each. Metric: entries you can't trace to a deliberate install.

**Affected:** Postman desktop 12.33.4 in the report, and a commenter saw the same moving from 12.31.3 to 12.35.1 · **Fixed in:** not stated, no fix confirmed · **Severity:** not stated by Postman, the reporter labels it severe · **Stopgap:** remove the Postman plugin, hook and MCP entries from the agent configs, which Postman says can be done from inside the app · **If compromised:** not stated
[Source](https://github.com/postmanlabs/postman-app-support/issues/14370)

## 🔬 A coding-agent harness lost about two thirds of its SWE-Bench score as it kept evolving
A Tsinghua group asked whether a coding agent whose harness keeps rewriting itself can hold onto what it learned. With DeepSeek-V4-Flash-0731, Meta-Harness raised SWE-Bench to 94.0%, then fell to 32.0% by round 5 after evolving on FeatureBench, a 66% relative drop. Of the pass-to-fail cases, 87.1% were verification conflicts, where new rules clashed with old checks. Code is at github.com/THU-Agent/continual-harness-evolution.

It's a preprint on small task subsets, so read it as a warning rather than a measurement of your system. If your harness learns from its own runs, rerun the old tasks after every change and watch the verification and submission rules first.
[Source](https://huggingface.co/papers/2611.03219) · [The paper](https://arxiv.org/abs/2611.03219)

## ✍️ Harrison Chase: the hard part of agents is still deciding what to remember
Chase's 2 November post pushes back on the idea that agent architecture is settled: an LLM in a loop, calling tools, in a sandbox. His view is that always-on agents bring fresh context problems. Calibrating when a background agent interrupts you is hard, and he writes that "the hardest part of the intelligence layer is figuring out what to remember."

The practical piece is async work. As subagents run longer, the main agent has to stay responsive, get told when background work finishes, and handle work paused for human approval. If your harness polls or blocks, that's the design to revisit.
[Source](https://www.langchain.com/blog/context-engineering-challenges-late-2026)

## 🏗️ Docker Sandboxes had a copy command that let an agent reach the host
Endor Labs published CVE-2026-103916 on 3 November. A sandboxed agent plants a symlink in its workspace, and when the operator later runs `sbx cp`, the CLI resolves the link on the host, bypassing the sandbox allowlist. Endor says copy-out could overwrite host files such as shell configs and SSH keys. Docker fixed it in v0.51.0 after an earlier fix was found incomplete.

The write-up notes that a prompt-injected agent could set this up. The takeaway is that the sandbox boundary includes the tools you use to move files across it. Resolve paths before you trust them, and prefer directories the sandbox has never mounted.

**Affected:** Docker Sandboxes `sbx` CLI before v0.51.0, the page gives no explicit range · **Fixed in:** v0.51.0 · **Severity:** High, CVSS 3.1 8.2 · **Stopgap:** run `realpath` on copy source and destination and check they stay inside the workspace · **If compromised:** not stated in the advisory
[Source](https://www.endorlabs.com/learn/docker-sandboxes-vulnerability-lets-ai-agents-access-sensitive-files-outside-their-sandbox-cve-2026-103916)
