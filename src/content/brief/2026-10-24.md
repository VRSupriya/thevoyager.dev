Saturday's thread is trust at the edges: the bytes your agents download, and the claims vendors make about their own models and tools.

## 🔥 A Brotli decoder bug can give code execution through Node and Python
Node.js shipped security releases on 21 October. One of the four High fixes, CVE-2026-111497, is a Brotli update in 24.22.1 (and matching 22 and 26 releases, per Aikido). Aikido's write-up says it is an out-of-bounds write in Google's Brotli decoder, in versions 1.0.3 through 1.2.0, that can lead to remote code execution. Python's `Brotli` and `brotlicffi` packages are affected up to 1.2.0 and fixed in 1.2.1 and 1.2.1.0.

Anything that fetches compressed content from servers you don't control is in scope, and agents with web tools do exactly that all day. Upgrading is the only fix, and images that bundle their own runtime have to be rebuilt. The Node.js notes give no exploit details or in-the-wild reports.

[Source](https://nodejs.org/en/blog/release/v24.22.1) · [Aikido write-up](https://www.aikido.dev/blog/python-packages-vulnerable-node2shell-brotli-cve-2026-111497)

## 🚀 Kimi K3.1 Pro: 1M context now, open weights promised by 4 November
Moonshot's new flagship is live on its API and apps. It has a 1M-token context window and the hosted price is $2 per million input tokens and $10 per million output, according to Simon Willison. Moonshot says full weights arrive by 4 November. By Moonshot's own numbers it scores 65.7% on Terminal-Bench 4.0 against 66.4% for Claude Opus 5.5, and cuts its hallucination rate on its own hard benchmark from 23.4% to 8.3%. Artificial Analysis gives it 55 to Opus 5.5's 58.

So it is a credible, cheaper option for long-running agent work, with two open questions: the licence, and how it behaves outside Moonshot's tests. A "Highspeed" tier is 2-3x faster at twice the price. Until weights ship, treat it as a hosted API with a promise, not an open model.

**Try this:** replay a week of your agent's real tasks on K3.1 Pro and your current model, and compare task success and cost per completed task.

[Source](https://www.kimi.ai/blog/kimi-k3-1-pro) · [Simon Willison](https://simonwillison.net/2026/Oct/23/kimi-k31-pro/)

## 🤖 LangChain parks big tool results in files, and lets the agent page through them
LangChain's Deep Agents write any tool result over roughly 20,000 tokens to a file under `/large_tool_results/`. The agent gets the path and a short preview, then reads it 100 lines at a time. The post's example is a weekly competitor-research agent and a 40,000-row export that would never fit in a prompt.

The design choice worth stealing is that retrieval becomes the default way to look at your own tool output. It keeps the context small and the cost flat, but every read is another model turn, so latency grows with how often the agent needs the detail. The post doesn't say how often that happens.

[Source](https://www.langchain.com/blog/context-engineering-starts-with-retrieval)

## 🔬 A small verifier makes coding agents better for about 10% more money
SWE-Verifier is a 4B-parameter model, trained from Qwen3.5-4B, that scores a coding agent's proposed actions, decides when to sample more candidates, and ranks them before anything runs. The authors report MiniMax-M2.7 going from 75.47% to 77.20% at 1.09x cost, and DeepSeek-V4-Flash from 72.60% to 74.27% at 1.13x. It checks fewer than 4% of steps. Model, code and data are released.

The gains are small and come from the authors' own runs, so read it as a cheap pattern rather than a leap. Spending verification only where the agent is unsure is a better budget than verifying everything.

[Source](https://arxiv.org/abs/2610.30284) · [Code](https://github.com/zkjzou/SWE-Verifier)

## ✍️ Modal's CEO on why GPU contracts are "rectangles" and sandboxes are the new growth
On Latent Space, Erik Bernhardsson argues that fixed GPU contracts are rectangles while real demand isn't, so Modal pools demand across customers to sell elastic capacity. Sandboxes, driven by coding agents, background agents and RL, are now roughly a third of Modal's revenue. Fast startup, through GPU buffers, checkpointing and memory snapshots, is the core of the product.

He also flags the financial risk of locking in GPU supply at high prices. If you size capacity for agents, it's worth asking how bursty your own load is before you sign a reservation.

[Source](https://latent.space/p/modal-d/)

## 🏗️ Agents wrote half the code with declarative pipelines, and a bit more wrong answers
Databricks had Opus 4.8 build 528 data pipelines (22 tasks, 12 datasets, two styles). Declarative pipelines had a median of 64 lines against 131, and used 17 executor-seconds against 596. They cost more to build: about 2.3x the tokens, roughly $0.50 against $0.26 per build. Pipelines that ran cleanly but gave wrong answers were 32.2% for declarative against 27.7% for procedural.

It's Databricks measuring its own product, and a wrong-but-green pipeline in either style is the failure that matters. The consequence for architecture is that checking results, not just completion, has to sit outside whatever the agent writes.

[Source](https://www.databricks.com/blog/built-agents-case-spark-declarative-pipelines)
