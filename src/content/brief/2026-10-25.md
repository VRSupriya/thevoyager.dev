Sunday's theme is permissions: what a stolen app can do, what a default can quietly change, and who is judging your outputs.

## 🔥 An agentic pentest framework drove the ConnectWise attack, Microsoft says
Microsoft attributes the ConnectWise Cloud Backup compromise to Storm-0940, a China-aligned group using ARTEX, an open-source framework that runs LLM agents through a whole intrusion. After the compromise it tried sign-ins to more than 2,250 tenants. In some environments the agents went past login: they queried Microsoft Graph, added application credentials and changed privileged roles.

```stats
2,250+ | tenants the group tried to sign in to after the ConnectWise compromise (Microsoft)
2,900/min | failed sign-ins at the peak of the earlier password spray
< 3 hours | from first targeting to privileged cloud access in several attacks
```

The lesson is less about the AI and more about speed. A multi-tenant app with high privileges is now a thing that gets used within hours, so review service-principal permissions by application ID, not by name. Microsoft advises keeping the affected apps disabled and preserving evidence before deleting anything. It did not say how many organizations were actually compromised.

[Source](https://www.microsoft.com/en-us/security/blog/2026/10/21/storm-0940-uses-artex-agentic-ai-connectwise-supply-chain-compromise/) · [CyberScoop](https://cyberscoop.com/microsoft-attributes-connectwise-supply-chain-attack-china-storm-0940/)

## 🚀 NVIDIA's Dory is a 4B model that can loop longer when it needs to
Dory 1.0 is a looped, latent-recurrent model: 4B parameters, up to 256K tokens of context, released 16 October under the OpenMDW licence. It reuses its layers in a loop, and the card says you can change the loop count at inference without retraining. That makes compute a dial rather than a model-size choice.

If it holds up, one small model could serve both cheap routing and harder reasoning, with latency you set per request. NVIDIA's benchmark table, run on its own harness, is the only evidence so far. It reports scores at 1, 2 and 4 loops (SWE-bench Verified 50.3, 59.5 and 61.8), recommends 2 loops by default and 4 for agentic tasks. Each extra loop normally adds its own KV cache; the card's `last_loop` cache mode keeps memory at the one-loop size.

**Try this:** run your own eval set at two loop counts against your current small model, and compare accuracy, latency and cost per task.

[Source](https://huggingface.co/nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-BF16)

## 🤖 Google ADK 2.13 moves default tracing to OpenTelemetry GenAI v2
ADK 2.13.0, released 22 October, makes OpenTelemetry GenAI v2 (`otel_semconv_1_44`) the default and removes the `call_llm` span. Set `ADK_TELEMETRY_SCHEMA_VERSION_OPT_IN=otel_semconv_1_36` to keep the old schema. The release also promotes 12 experimental features to stable, adds barge-in for live audio and experimental MongoDB session and memory services, and claims up to 8x faster execution turns for string-model agents.

The telemetry switch is the one to read twice. Dashboards, alerts and cost reports keyed on `call_llm` will go quiet without an error. Pin the opt-in, upgrade on a branch, then migrate queries on your schedule.

[Source](https://github.com/google/adk-python/releases)

## 🔬 Your LLM judge matters more than your prompting strategy
A new study ran nine prompting strategies, including chain-of-thought and role conditioning, through four open-weight judge models across 27 languages and 13 datasets, over a million scores in all. The judge model mattered more than the strategy, and effects sometimes reversed between judges. Stability dropped in low-resource languages, where averages hid it.

So a judge prompt tuned on English with one model isn't evidence for another model or language. For multilingual products, validate the judge against human labels per language before trusting a dashboard. It's a preprint, and I found no linked code.

[Source](https://arxiv.org/abs/2610.31172)

## 🏗️ Treat each agent task as an actor with a mailbox
In an InfoQ talk, Manju Rajashekhar argues production agents are distributed systems and fit the actor model. Everything is a message to one mailbox per task: chat input, tool results, cancellations. State has one owner and is written through as it changes, so crash recovery is just resumption. Failures are handled by supervisors with restart, retry or escalate policies, and waits become recorded state rather than blocked call stacks.

It's a design lens, not a product, and he says no mainstream agent framework clearly implements it. But "what are the actors, what state does each own, who supervises whom" is a useful review question for any agent runtime.

[Source](https://www.infoq.com/presentations/actors-for-production-ai-agents/)
