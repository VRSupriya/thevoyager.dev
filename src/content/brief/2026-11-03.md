Today has one date worth putting in a calendar and four ideas worth an afternoon. The date comes first.

## 🔥 GitHub will block pull_request_target by default on 2 December
From 2 December 2026, GitHub Actions blocks `pull_request_target` events by default in public repositories on Free, Team and Enterprise Cloud. Private and internal repositories aren't affected. The change was first scheduled for 2 November and moved back a month. Before that, brownouts on 9 and 16 November (16:00 to 18:00 UTC) make blocked workflows fail with an error annotation; between them the rule only warns.

If you run a labeler, a triage bot or an AI review agent on that trigger in a public repo, expect it to fail unless you allow it through an Actions event policy, which can be scoped to specific workflow files. The trigger runs with the base repo's secrets on code from a fork, which is why GitHub is closing it. The usual way out is to split the job: an unprivileged workflow that reads the fork's code, and a trusted one that only posts results.
[Source](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2)

## 🤖 Google Cloud's docs become an MCP plugin inside Antigravity
Google's Antigravity marketplace now has a `google-cloud-developer` plugin, installed with `agy plugin install google-cloud-developer`. It bundles a Developer Knowledge MCP server that is pre-authorized by default, with no API keys or OAuth setup. Google's pitch is that coding agents invent deprecated SDK syntax and guess invalid command flags without cloud-specific context.

The plugin adds guardrails too: least-privilege IAM, and consent before it enables billable APIs or changes infrastructure. It grounds you in Google's own docs (Cloud, Firebase, Android, Web, Gemini), not the rest of your stack.

**Try this:** give your agent 10 gcloud or SDK tasks it currently gets wrong, with and without the plugin. Metric: how many outputs need a manual fix.
[Source](https://cloud.google.com/blog/topics/developers-practitioners/google-cloud-developer-plugin-now-available-in-antigravity-marketplace/)

## 🔬 A frontier model edits a small model's weights by hand, and it works once
A 2 November post from Rikiya Takehi, Jayden Teoh, Alex Zhang and Omar Khattab (MIT CSAIL) says GPT-6 Astra can read and write network weights directly, with no gradient descent. Astra traced a looping habit in Qwen3.5-0.8B to one direction in two MLP layers and edited 131,072 weights (0.016%). With 50 forward passes, MATH-500 went from 7.9% to 48.1%.

It's one small model, and the same approach failed on Gemma 3 270M. The authors write that editing "could remove an obstacle that hid an ability, but it could not add an ability the model lacked." An edited checkpoint and logs are public, so the numbers can be checked.
[Source](https://rikiyat.github.io/blog/weight-space-programming/)

## ✍️ Philipp Schmid: agents are collapsing their tools into one exec call
In a 1 November post Schmid argues that agents are moving toward a single tool, `exec`, where the model writes a script that chains actions inside a sandbox instead of calling one tool per turn. In his sketch about 80 JSON-Schema tools are compiled into TypeScript declarations, and one script fans out with `Promise.all`. His Linear example makes 55 underlying API calls and returns a single line.

The security work moves to the host bridge, which can inject OAuth tokens outside the sandbox, validate schemas and pause for confirmation on destructive calls. His Linear example archives issues with no confirmation step, and the demo's Node `vm` sandbox carries a comment to use QuickJS or isolated-vm for untrusted code.

**Try this:** wrap one MCP server with 20+ tools behind a single sandboxed exec. Metric: model round trips and tokens per task, against your current per-call setup.
[Source](https://www.philschmid.de/code-mode)

## 🏗️ NVIDIA publishes Kubernetes recipes for Vera Rubin, in Preview
On 2 November NVIDIA released AI Cluster Runtime (AICR) v1.0.0 with a Vera Rubin NVL72 recipe family, marked Preview, covering training, inference and Dynamo variants on Ubuntu with RKE2. The training recipe has 14 components, including GPU Operator v26.7.0 and DRA driver v0.5.0, and needs Kubernetes 1.34.1 or later. NVIDIA reports 8 of 8 conformance checks passing and 744.71 GB/s busbw at 16 GiB for a cross-node NCCL all-reduce.

Inference performance isn't validated: NVIDIA notes that vLLM's published images through v0.28.0 are built against CUDA 13.0.3, while Rubin kernels need CUDA 13.4 or later. Host-managed IMEX and DRA-managed ComputeDomains can't share a node, which is the kind of constraint to settle before you plan capacity.
[Source](https://developer.nvidia.com/blog/making-kubernetes-ai-ready-for-nvidia-vera-rubin-on-day-one/)
