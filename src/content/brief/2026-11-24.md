Today's thread is who gets to say yes. An agent that can approve a pull request, a gateway that forgets its own allowlist, a grader that fails good work: each one is a decision someone assumed was being made carefully.

## 🔥 Claude Ship puts review, fixes and approvals on your pull requests
Anthropic launched Claude Ship on 23 November: three agents for GitHub pull requests. Code Review (generally available) comments on issues by severity. PR Steward and Claude Approvals are in public beta: Steward fixes failing checks and conflicts, and Approvals can post an approving review where a policy file in your repo allows it.

It covers Team and Enterprise plans on GitHub only, bills on tokens, and excludes Zero Data Retention, the HIPAA configuration and customer-managed keys. The docs warn that auto-merge or a merge queue with no human requirement can still land a change nobody looked at, so your branch protection is now part of the agent's design.

**Try this:** run Approvals in observe mode on one low-risk repo for two weeks. Baseline is your human review time and revert rate; the metric is how often the check agrees with your reviewers. Observe mode is billed too, so set a spend limit first.

[Source](https://claude.com/resources/articles/introducing-claude-ship) · [Docs](https://code.claude.com/docs/en/claude-ship) · [PR Steward security](https://code.claude.com/docs/en/pr-steward-security)

## 🚀 GLM-5.4 runs the same layers twice
Z.ai's GLM-5.4 is what it calls its first Loop Transformer: 28 layers of the GLM-5 base model reused across two iterations, with a 1M-token context and 128K maximum output, according to its docs. The Model API arrives "upon completion of the security assessment"; for now it's reachable through a Coding Plan. Simon Willison notes it isn't open weights, at least not yet.

The trade is clear even without benchmark scores in the docs: more compute per token from the same parameter count, plus the cache design to go with it. But with no weights and no price, you can't size it or serve it yourself. Treat it as a design idea to watch, alongside Thinking Machines' looped models, until someone publishes numbers you can check.

[Source](https://docs.z.ai/guides/llm/glm-5.4) · [Simon Willison](https://simonwillison.net/2026/Nov/23/glm-54/)

## 🤖 Netflix wrote its codebase a second set of readers
At QCon SF, Netflix's Mark Khuzam described rebuilding the SDLC for coding agents, as InfoQ reports. Netflix wrote 45 architecture decision records meant for both people and agents, kept more than 300 other documents discoverable, and put an AGENTS.md file in repos that plays the part of robots.txt for agents. Its first AI code reviewer left 23 comments on one PR; it now posts only verified blockers with evidence and the rule they break.

The speaker's own results: developer NPS for the internal framework went from -3 to +25 over three quarters, and 32% more PRs year over year. His summary: "None of this is new. It's good engineering, built for a new reader." If your agents keep making the same mistake, the fix is probably a document, not a prompt.

[Source](https://www.infoq.com/news/2026/11/netflix-sdlc-ai-coding-agents/)

## 🔬 Asking an LLM how slow your model will be is a bad idea
A preprint submitted on 19 November, PreRun, measures how well models predict inference latency before a run: 64 configurations, three launches each. Zero-shot, open-weight LLMs underestimated latency by 90–99% on held-out configurations, and Claude's zero-shot error was 4.5 times that of a Random Forest trained on 32 configurations. Five labelled examples helped Claude a lot.

For capacity planning, that points at a boring answer: measure 30 or so of your own configurations and fit a small regressor. The authors say data and pipeline will be open-sourced upon acceptance, so for now it's a result to reproduce, not a tool to install.

**Try this:** benchmark 30 of your serving configurations, fit a Random Forest, and compare its error against asking your favourite LLM for the same numbers.

[Source](https://arxiv.org/abs/2611.26875)

## ✍️ Eugene Yan on why public evals mislead
Eugene Yan went through twelve public evals and found evidence in eight that the grader failed work that should have passed. He adds that average pass rate hides a large difference in production, and that a cheap failure can look efficient on a leaderboard while costing engineers review time.

Before you trust a leaderboard number, read a handful of failed traces yourself. If the grader is wrong in a third of the cases you check, the ranking says more about the grader than the models.

[Source](https://eugeneyan.com/writing/public-evals)

## 🏗️ LiteLLM fallbacks can skip the model allowlist
A LiteLLM advisory published on 23 November says team and key `router_settings` fallbacks can route requests to models the caller isn't allowed to use. It's rated Moderate (CVSS 3.1 5.4), with no CVE. From 1.100.0 you can turn on `general_settings.enforce_fallback_model_access`; from 1.108.0 the check is on by default.

The design lesson outlasts the bug: access control that lives on the primary route but not on the retry path isn't access control. If you run a gateway, test your allowlist with the primary model failing on purpose.

**Affected:** >=1.80.15, <1.108.0 · **Fixed in:** 1.108.0 · **Severity:** Moderate, CVSS 3.1 5.4 · **Stopgap:** set `general_settings.enforce_fallback_model_access: true` (from 1.100.0) · **If compromised:** not stated in the advisory

[Source](https://github.com/BerriAI/litellm/security/advisories/GHSA-wpm4-hgr2-xjwr)
