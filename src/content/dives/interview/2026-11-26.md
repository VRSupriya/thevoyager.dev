A shopper searches "waterproof hiking boots", ticks "size 43", "in stock nearby" and "under 120". The unfiltered results were great. The filtered page has two items, one of them a sock.

The index didn't break. It was never asked the question it was built for. Approximate indexes find the nearest vectors first, and a filter then throws most of them away.

This is a practice question in the style of a Google loop for a Senior AI/ML Engineer. It isn't a reported question, and I haven't checked any company's current interview format. It builds on [Monday's building block](/deep-dives/models-agentic/2026-11-23) and [Wednesday's 50-million-product design](/deep-dives/system/2026-11-25).

## The question

*"You own retrieval for a catalogue of 50 million products. Every query carries a text part and filters (category, brand, price, stock by region). Offline, recall@10 is 95%. In production, filtered queries look worse and nobody can say by how much. Design the retrieval layer, then tell me how you'd find out what's broken."*

The panel wants you to separate three things: what the index does, what the filter does to it, and how you'd measure.

## Pause: answer out loud for 10 minutes first

Order to use: how the filter meets the index, then selectivity bands, then hybrid scoring, then measurement, then cost.

## A framework that works here

**1. Name the three places a filter can run.** Before the index search (pre-filter: find the matching set, then brute-force it), after it (post-filter: take the nearest candidates, drop the non-matches), or during it (in-index: the graph traversal itself skips non-matching nodes). Everything else is a consequence of which one you picked and how many items the filter passes, its selectivity.

**2. Show why post-filtering is the trap.** pgvector's README says it directly: with approximate indexes, "filtering is applied after the index is scanned", so a condition matching 10% of rows with the default `hnsw.ef_search` of 40 returns about 4 rows on average (README for v0.8.7, read 26 November 2026). Ask for 10 results and you get fewer.

**3. Give selectivity bands, not one answer.** There's no single best strategy, and saying so is the senior move.

The same post shows the fixes are not interchangeable. Extra graph edges built per payload field won on single filters but gave 63.7% on a 4% two-field AND filter, because edges are built per field, never per combination. ACORN, a search-time repair that also walks neighbours of neighbours, rescued that case but cost 2.1x to 2.9x the plain graph's latency on single filters and stalled at 67.7% on the 1% filter.

**4. Say what to do at each end.** Very tight filters (roughly the bottom 1%): don't use the graph. Read the matching IDs from a payload or inverted index and score them exactly; in Qdrant's run, on the 0.012% two-field filter this gave 100% recall in 1.3 ms while both graph variants scored under 2%. Middle bands: in-index filtering with an edge-repair method. Loose filters: plain post-filtering with a bigger candidate list is fine. The planner part, choosing per query from an estimated selectivity, is what a production system needs.

**5. Put hybrid scoring in its own sentence.** Keyword and vector scores aren't comparable, so fuse by rank (reciprocal rank fusion, RRF) or learn a weighting. Google Cloud's Vector Search docs describe exactly this: dense and sparse distances "can't be directly compared", so results are merged by RRF with an alpha that moves between sparse-only and dense-only (docs read 26 November 2026). Treat the fusion method as a hypothesis, then test it; [Wednesday's design](/deep-dives/system/2026-11-25) shows a case where RRF lost an A/B test.

**6. End with measurement.** Sample real filter combinations from logs, bucket them by selectivity, compute recall@10 against exact search per bucket, and report the worst bucket as well as the mean.

## A model answer, compressed

> [!REVEAL] Show the answer
> "I'd begin with the filter, not the index. Each query has a text part, a vector part and a predicate, and the predicate's selectivity decides whether an approximate index can serve it. So the first design artefact is a histogram of selectivity over real traffic.
>
> Retrieval runs two legs, lexical and vector, each with the filter applied inside the leg, then rank-fused and reranked. For the vector leg, I'd use an engine with in-index filtering and a planner: loose filters stay on the graph, mid-selectivity ones use edge repair, and very selective ones skip the graph and score the matching IDs exactly. I'd also set `k` and the candidate list from the selectivity estimate rather than fixing them.
>
> Memory is separate arithmetic: 50M vectors at 1,024 dimensions are about 205 GB as float32 and about 51 GB as int8, so I'd quantise and rescore with full-precision vectors from disk.
>
> To find what's broken, I'd replay logged filter combinations against exact search, bucket by selectivity and by filter shape, and plot recall per bucket. I'd expect the damage in the tightest buckets and in multi-field AND filters, since per-field index tricks don't cover intersections. Then I'd put recall per bucket on a dashboard with an alert, because filters change as the catalogue changes.
>
> Cost: the filter strategy mostly trades latency for recall, so I'd quote recall and p95 per band, not one number."
>
> **Security and failure modes:** Filters double as access control (region, tenant, embargoed products), so they must be enforced on the server with identity from the session, never from a client-supplied filter string. A filter that silently returns too few rows is a quality failure, and a filter that is dropped on error is a data-exposure failure: fail closed, return fewer results. A shared index lets one tenant's vectors affect another's recall, which pgvector's own README flags; separate partitions where isolation matters. Stock and price changes must flow to the index quickly, or the filter lies.
>
> **Alternatives:** Managed vector search (Google Cloud's Vector Search, built on ScaNN) when you want filtering, sparse and dense search and RRF as a service; Postgres with pgvector when the catalogue already lives there and filters are selective enough for exact plans; an engine with a query planner (Qdrant, Elasticsearch/Lucene) when filters vary widely. The table below says what flips each choice.

## What top candidates add at this level

- **They ask for the selectivity distribution first,** and say they'd rather see it than guess it.
- **They know the planner can be wrong.** The February 2026 UC Merced study found pgvector's cost-based optimiser often chose approximate scans when an exact sequential scan would give perfect recall at comparable latency, so they check plans with `EXPLAIN ANALYZE`.
- **They refuse a blended recall number.** Qdrant's own table shows a 39.7% case under a planner with ACORN off, next to cases at 98%.
- **They note that benchmarks are vendor-run** and say what they'd re-run on their own catalogue.
- **They treat the filter as a security boundary,** not only a relevance tool.

## One tip

Start the whiteboard with a three-row table: selectivity above 20%, between 1% and 20%, under 1%. Put a strategy in each row before you name a database. It shows you're designing for the data, not reciting a product.

## Threat model and failure modes

- **Filter injection and client-trusted filters.** If the client sends the filter expression, a user can widen it to see another region's or tenant's products. Mitigation: build the predicate server-side from the authenticated identity; expose only whitelisted fields to the client.
- **Fail-open on filter errors.** A planner timeout that falls back to unfiltered search leaks restricted items. Mitigation: on failure return fewer or no results, never the unfiltered set. This is the safe direction.
- **Cross-tenant recall and cache effects.** A shared approximate index lets one tenant's vectors affect another's recall and speed (pgvector README); a shared result cache keyed without the filter can serve one tenant another's answers. Mitigation: partitions or separate indexes per tenant, and the full predicate in every cache key.
- **Silent recall loss.** Tight filters return few or irrelevant items and nothing errors. Mitigation: per-bucket recall against exact search in CI and in production sampling, with an alert on the worst bucket.
- **Stale attributes.** Price or stock changes lag the index, so filters show items that are gone. Mitigation: an update path with a freshness SLO, and a final check against the source of truth before display.
- **Runaway cost.** Raising candidate counts everywhere to rescue tight filters multiplies latency and compute. Mitigation: route by estimated selectivity, and cap candidates per query.

## Alternatives and when to switch

| Option | What it gives you | When to switch |
|---|---|---|
| Managed vector search (Google Cloud Vector Search, ScaNN-based) | Dense, sparse and hybrid queries, RRF with an alpha, token and numeric restricts | Switch away if you need filter behaviour you can tune per query, or the restrict count grows (docs say many restricts raise memory use and shard count) |
| Postgres + pgvector | One store, SQL filters, iterative scans from v0.8.0, partial indexes and partitioning | Switch away when filters are mostly broad, the index no longer fits memory comfortably, or you need cross-tenant isolation beyond partitioning |
| Engine with filter-aware planner (Qdrant, Lucene-based search) | In-index filtering, ACORN-style repair, exact fallback for tight filters | Switch toward it when selectivity varies widely across queries; switch away if you can't operate another cluster |

## Ten-minute practice

Take any catalogue you can query. Pull 200 real filter combinations, compute each one's selectivity, and bucket them under 1%, 1% to 20% and over 20%. Then run exact search and your index for each query and compare recall@10 per bucket.
